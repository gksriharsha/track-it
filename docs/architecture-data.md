# TrackIt — Data Architecture

**Status:** decided, executable. **Date:** 2026-09-03.
**Companion:** [`data-findings.md`](./data-findings.md) — the measured evidence. This document is
the design that follows from it. Every number below was re-measured against
`/Users/kgundu1/BioBalance/data/raw/extracted/` while writing it; commands that reproduce each
figure are in §7.

**The invariant this whole architecture exists to protect:**

> "No measured selenium for this food" must never render as "0 mcg", and a daily total must never
> be presented as complete when it is not.

Everything else — file layout, key types, index choices — is negotiable. That is not.

## 0. Decisions at a glance

| # | Question | Decision | Why |
|---|---|---|---|
| 1 | Which USDA data is bundled? | Foundation 2026-04-30 (469 foods) + SR Legacy 2018-04 (7,793) + FNDDS 2024-10-31 (5,432) = **13,694 foods** | Measured **17.88 MiB** on disk / **5.52 MiB** compressed. Branded (2.0 M foods, 2.9 GB) is not bundleable. |
| 2 | Iodine? | ARS Iodine DB Release 4 as a build-time overlay, joined on **column B**, not column A | Takes iodine from 0 rows in SR Legacy to **382 bundled foods** with a real measured value |
| 3 | Barcodes? | Online-only, cached locally. Macros + the four FDA-mandatory micros. Never a micronutrient panel | 21 CFR 101.9 mandates only vitamin D, calcium, iron, potassium |
| 4 | Nutrient storage | **LONG** (one row per food × nutrient), never WIDE | Provenance is per-value; absence must be an absent row |
| 5 | "Not measured" | **An absent row.** `amount REAL NOT NULL` | There is no NULL to `COALESCE(…, 0)` |
| 6 | Value type | 7-variant tagged union + 6 CHECK constraints (verified rejecting all 7 invalid states) | Makes the invalid state unrepresentable in the file, not just in Rust |
| 7 | Aggregation | `[lower, upper]` + mass-weighted coverage + bounded/unbounded flag | %RDA reads the lower bound; %UL reads the upper. One scalar cannot do both |
| 8 | One DB file or two? | **Two.** `usda_core.db` (bundled, read-only) + `user.db` (WAL, mutable) | See §5.1 — the objection to two files was an argument against `tauri-plugin-sql`, which we are not using |
| 9 | SQL layer | `rusqlite 0.40` (bundled SQLite 3.51.3) behind `#[tauri::command]` | Nutrient values cross IPC as a serde-tagged enum, never as `null` |
| 10 | Log → food reference | `(food_kind, food_ref)` breadcrumb + a **content-addressed nutrient snapshot** carrying the FK | A USDA release that drops an `fdc_id` must not silently change a past day's totals |
| 11 | Built DB in git? | **No.** Generated by a checked-in script; the manifest, assertions and `dri.json` are committed | 17.88 MiB binary that changes wholesale twice a year |

## 1. Food data strategy

### 1.1 What ships in the binary

Measured on the archives already in `data/raw/`:

| Dataset | Release | Foods | Nutrient rows (tracked set) | Portions | Role |
|---|---|---:|---:|---:|---|
| SR Legacy | 2018-04, frozen | 7,793 | 371,838 | 14,449 | **The backbone.** Broadest nutrient list (82.7 nutrients/food mean) |
| FNDDS / Survey | 2024-10-31 | 5,432 | 266,119 | 22,046 | "As consumed" mixed dishes; the best household portions in FDC |
| Foundation | 2026-04-30 | 469 | 11,156 | 187 | Newest lab work; small, and a supplement — never a replacement |
| **Bundled total** | | **13,694** | **649,113** | **36,679** | **17.88 MiB / 5.52 MiB gz** |

Excluded, deliberately:

| Dataset | Size | Why not |
|---|---|---|
| Branded Foods | 2.0 M foods, 428 MiB zip / ~2.9 GB CSV; 146 MB even deduped to a GTIN index | Not bundleable. Mean 13.0 nutrients/food. Magnesium 3.0%, zinc 2.6%, selenium 0.8%, chromium 0.23% |
| Experimental Foods | — | No bulk download exists, and USDA states they "are for research purposes and may not be appropriate as a reference for the consumer or for diet planning" |
| Open Food Facts bulk dump | 11.9 GiB JSONL / 1.19 GiB CSV | Unshippable, and ODbL share-alike would attach to a redistributed file |

**Size discipline.** If the bundle ever needs to shrink, prune *nutrients*, not foods: the tracked
set already drops 369,486 untracked rows (36% of the raw 1,018,599). Dropping foods removes search
hits, which is what users actually notice.

**A dropped index, measured.** `INDEX ix_rfn_nutrient(nutrient_id, fdc_id)` costs **7.47 MiB** and
made the query it exists for ("top 10 foods by selenium") *slower by 0.06 ms* — the `ORDER BY
amount DESC` forces a sort either way, and a 649 k-row scan is 6.7 ms. It is not built. This is why
§7 asserts on the built file's size: a silent index addition costs 42% of the DB.

### 1.2 Two Foundation Foods traps

**Trap 1 — select on `food.csv`, not `foundation_food.csv`.**

```
food.csv WHERE data_type='foundation_food'  → 469 foods, 21,459 nutrient rows, 187 portions
foundation_food.csv                          → 395 foods, 17,008 nutrient rows
```

The 74-food delta is not junk. It includes *Tomato, roma*; *Melons, cantaloupe, raw*; *Apples,
granny smith, with skin, raw*; *Mushrooms, shiitake*; *Cheese, ricotta, whole milk*; and both
*Soy milk* and *Almond milk, unsweetened, plain, shelf stable*. Joining through
`foundation_food.csv` silently drops them. `foundation_food.csv` is used for exactly one thing:
`NDB_number`, needed by the iodine join.

Also filter hard: `food.csv` in the Foundation archive has 87,990 rows, of which 87,521 are
laboratory records (`sub_sample_food` 75,055, `market_acquisition` 7,577, `sample_food` 4,079,
`agricultural_acquisition` 810). Same for `food_portion.csv`: 10,951 rows, of which only **187**
belong to the 469 foundation foods.

**Trap 2 — energy lives under 2047, not 1008.** Measured over the 395-food set (reproducing
`data-findings.md` exactly): 1008 = 24.1%, 2047 = 81.5%, 2048 = 72.9%, **any of the three = 81.8%**
(80.6% over the 469-food set we actually bundle). Reading 1008 alone loses calories for three
quarters of Foundation. See §2.2 for the resolution chain.

### 1.3 The ARS Iodine overlay

`data/raw/extracted/iodine/Iodine Database_Release 4_Per 100g.xlsx`, one sheet, 520 rows.

| Row class | Count |
|---|---:|
| Title + header | 2 |
| Category section headers (`Dairy and Eggs`, `Seafood`, …) | 20 |
| Footnote rows | 20 |
| **Food rows with a description and an iodine value** | **478** |
| …of which carry an identifier in column B | 384 |

**The join key is column B, `"Standard Reference (Foundation Foods) FDC NDB No."` — never column A
`DB_ID`.** `DB_ID` is an internal ARS sequence: the *Butter, salted* row is `DB_ID=91`,
`NDB No.=01001`, `TDS No.=164`. Joining `DB_ID` to `sr_legacy_food.NDB_number` produces a clean,
fully-populated, entirely wrong iodine column.

Column B is not a plain integer. The parser must handle four observed forms:

| Form | Example | Meaning | Resolve to |
|---|---|---|---|
| Zero-padded NDB | `01001` | SR Legacy NDB | `sr_legacy_food.NDB_number` (strip leading zeros; SR stores `18634`, not `018634`) |
| NDB + parenthesised code | `01253 (100297)` | SR NDB, plus the Foundation NDB for the same food | Prefer the SR match; the parenthesised code resolves via `foundation_food.NDB_number` |
| Parenthesised only | `(100299)` | Foundation-only food | `foundation_food.NDB_number` → `fdc_id` (**not** `fdc_id` directly — 0/12 match if you try that) |
| Asterisked | `18069*` | A *distinct food*: the iodate-dough-conditioner variant | Do **not** overwrite the plain row. Take the non-asterisk row; discard the `*` row in v1 |
| Slash | `16123/16124` | Two NDBs, one measurement | Skip (ambiguous) |

**Measured yield: 370 SR Legacy foods + 12 Foundation foods = 382 distinct bundled foods gain a
real iodine value**, each with `n`, mean, SD, min and max. The highest is NDB `02047`, *Salt, table,
iodized*, at 5,213.1 µg/100 g. Seven codes do not resolve (e.g. `43379` *Cheese, processed, Swiss,
low fat*), which the build reports but does not fail on.

Overlay rows are written as ordinary `ref_food_nutrients` rows with
`nutrient_id = 1100`, `value_kind = 'measured'`, `source = 'ars_iodine_r4'`, `data_points = n`,
`low = min`, `high = max`. They are the only non-FDC values in the bundled DB and are tagged as
such so the UI can cite them.

Iodine coverage after the overlay: 382 of 13,694 bundled foods (2.8%) — small, but the difference
between "iodine is a feature" and "iodine is a blank column".

### 1.4 Online tier, and what barcodes cannot do

```
scan → normalise to GTIN-14 → cached_foods → FDC /foods/search?query=<gtin>&dataType=Branded
                                           → OFF /api/v2/product/<gtin>.json
                                           → manual entry
```

Rules:

- **Normalise both sides to GTIN-14** (strip non-digits, reject non-numeric or >14, left-pad with
  zeros) before any comparison or cache write. USDA stores the same product as 12, 13 and 14
  digits inconsistently, and OFF canonicalises to its own form. Cache under the canonical code the
  API returns, not the scanner string, or one product becomes up to four cache rows.
- **All HTTP happens in Rust** (`reqwest` behind a `#[tauri::command]`), not in the WebView.
  `User-Agent` is *not* a forbidden Fetch header — that claim was refuted — but Chromium silently
  drops it (crbug 571722), and Tauri uses Chromium-family WebViews on Android. OFF requires a real
  UA. Rust also lets the same code path apply the §3 value rules before anything is stored.
- **OFF v2 returns HTTP 404** for a well-formed unknown barcode (`{"status":0,"status_verbose":
  "product not found"}`). The claim that v2 returns 200 for a miss was refuted; it does that only
  for a malformed code that normalises to `00000000`. Branch on status; still guard the JSON parse,
  because *transport* failures (503, 401) return HTML bodies.
- **The FDC API key is user-supplied**, pasted in Settings. Never ship a key. `DEMO_KEY` works for
  about four calls before 429 and is not a code path.

**What a barcode can deliver.** This is a legal ceiling, not a data-quality problem. 21 CFR 101.9
mandates only **vitamin D, calcium, iron and potassium**; vitamins A and C became voluntary in the
2016 rule. A label photograph physically cannot yield selenium, magnesium, zinc, folate or B12
unless the manufacturer volunteered it. Measured OFF presence in a 200-product US sample: calcium
80%, iron 85%, potassium 80.5%, vitamin D 51.5%, vitamin A 37%, vitamin C 41%, zinc 38%,
magnesium 39%, selenium 34%, B12 8.5%, folates 2.5%.

**What a barcode actively lies about.** Where a trace-mineral key *is* present, it is usually
zero-fill: selenium 0 in ~93% of products reporting it; vitamin K, choline and iodine 0 in 100%.
Barcode `0011110586780` "Colby Jack Cheese" reports `zinc=0, selenium=0, phosphorus=0,
magnesium=0, vitamin-a=0` — every one wrong for cheese. OFF also rescales non-nutrient fields
through its per-serving arithmetic (`nova-group_100g: 14.29` on a 1–4 ordinal), so iterating
`*_100g` keys into a nutrient table imports garbage. Whitelist the keys.

**Ingest rule for online sources** (see §3.2 for the type):

| Condition | Stored as |
|---|---|
| Key absent | no row → `Absent` |
| Key present, value > 0 | `LabelDeclared` (a point value; NLEA rounding is inside its precision) |
| Key present, value = 0, nutrient is FDA-mandatory or a macro | `LabelZero { upper }` with the 21 CFR 101.9(c) rounding increment as the bound |
| Key present, value = 0, any other nutrient | **no row** → `Absent` |
| `<nutrient>_modifier` = `'<'` | `BelowLoq { upper = value }` |

The "allowlist zeros through" variant of this rule was refuted: in products showing the zero-fill
signature, vitamin D is 0 in 89.3% of appearances, vitamin A 96.1%. Vitamins A, C and D get no
exemption; only vitamin D, calcium, iron, potassium and the macros do, because only those are
legally required to be there at all.

**Unit trap.** OFF reports every `_100g` value in **grams**, including micronutrients:
`vitamin-d_100g = 1.08e-05` means 10.8 µg. Reading it as mg is a 1000× error toward "you are
deficient". Never read `_value` — that is the contributor's raw number in the contributor's unit.

**Licensing.** USDA FDC is CC0 (attribution requested, not required). ARS Iodine DB is a US
government work. NASEM DRI *values* are facts; their table layout and footnote prose are not — we
store numbers and write our own caption text. OFF is ODbL: §4.5(c) exempts private use entirely,
so a personal build owes nothing, but OFF-derived rows live only in `user.db` (`cached_foods`) and
never in the shipped `usda_core.db`, which keeps the distributable file unambiguously CC0.

### 2.2 Resolution chains, and the measured cost of coalescing

A chain is evaluated **per food, in order, first hit wins**. The winning id is recorded in the row
(`source_nutrient_id`) so the UI can show it and so a bug is diagnosable. Chained ids are **never
averaged, summed, or coalesced**, because they are different measurements with different methods.
Measured worst cases, all reproduced today against Foundation 2026-04-30 / SR Legacy 2018-04:

| Pair | Foods carrying both | Differ >1% | Worst case |
|---|---:|---:|---|
| Energy 1008 vs 2047 | 104 | 62 | **Broccoli, raw: 31 → 39 kcal (+25.8%)**. (Kale, raw +22.9% is only second) |
| Energy 1008 vs 2048 | 98 | 28 | Ketchup, restaurant: 117 → 103 kcal (−12.0%) |
| Fiber 1079 vs 2033 | 19 | **19 (all)** | **Rice, white, long grain, unenriched, raw: 0.1488 → 2.771 g (+1,762%, 18.6×)**. Potato flour (+206%) is only fourth |
| Carbohydrate 1005 vs 1050 | 47 | **47 (all)** | **Eggs, Grade A, Large, whole: 0.96 → 0.20 g (−79.2%)**. Soy milk and almond milk have 1050 = 0.0 exactly — a manufactured zero |
| Sugars 2000 vs 1063 | 5 | **0** | They agree to <0.05%. This pair is a **coverage** split, not a value split: SR uses 2000 (77.1%) and never 1063; Foundation uses 1063 (39.4%) and barely 2000 (1.3%). Querying one id alone silently loses an entire dataset |
| 18:3 (1270) vs ALA (1404) | 1,963 | 884 | Frybread, Navajo: 0.004 vs 0.051 g (+1,175%) |

**ALA is not chained, and this is the sharpest rule in the model.** Nutrient 1270 is
*18:3 undifferentiated* — it includes γ-linolenic acid and trans isomers. It is not a safe upper
bound on ALA either: **24 SR Legacy foods have 1404 > 1270**, which is physically impossible since
ALA is a subset of 18:3 (*Cookies, shortbread, reduced fat*: 1270 = 0.167, 1404 = 0.582; *Veggie
burgers, unprepared*: 1270 = 0.0, 1404 = 0.081). The data is internally inconsistent in both
directions, so 1270 cannot substitute for ALA in either a deficiency or a sufficiency claim. If
1404 is absent, ALA is `Absent`. Same rule for LA (1316) vs 18:2 (1269).

### 2.3 The FNDDS join trap

`survey_food_csv_2024-10-31/food_nutrient.csv` stores **nutrient numbers, not FDC ids**, in a
column named `nutrient_id`. Measured: 65 distinct values, range **203–646**, of which **0 are
≥ 1000** and **all 65 match `nutrient.csv.nutrient_nbr`**. Foundation and SR Legacy use the FDC id
space (1001–2069) in the same column.

```sql
-- Foundation / SR Legacy
JOIN nutrient n ON n.id = fn.nutrient_id
-- FNDDS  (different column!)
JOIN nutrient n ON n.nutrient_nbr = fn.nutrient_id
```

Using the wrong one produces zero matches. With a `LEFT JOIN` and `COALESCE(amount, 0)` that is a
complete-looking, entirely-zero FNDDS food table for 5,432 foods — the exact failure this product
exists to prevent. The build asserts the joined FNDDS row count is **353,015**.

### 2.4 Provenance → `value_kind` mapping

Derivation codes come from `sr_legacy_food_csv_2018-04/food_nutrient_derivation.csv`. **The
Foundation archive does not ship that file**, so the SR Legacy copy is the mapping table for both;
the build asserts `1→A`, `3→AR`, `4→AS`, `49→NC`, `68→Z` and fails if the ids ever move.

| Source | Derivation | Rows (bundled) | `value_kind` |
|---|---|---:|---|
| SR / FF | `1` A, `2` AI, `3` AR, `4` AS | 155,838 + 24,543 + 1,811 + 17,524 … | `measured` |
| SR | `68` Z "Assumed zero" | **57,711, all of them zeros** | `assumed_zero` |
| SR / FF | `49` NC and all other calculated/imputed codes | ~112 k | `calculated` |
| SR | **blank** — 181,743 rows (28.2%), 31,989 of them zeros | | `unattributed` |
| FNDDS | **blank on 100% of 353,015 rows**; `data_points` also blank on 100% | | `calculated` — the FNDDS panel is complete by construction, i.e. imputed. Its 104,083 zeros (29.5%) carry no evidence and must never be labelled "measured" |
| ARS Iodine | n/a | 382 | `measured` |

**Analytical zeros stay `measured`.** Foundation has 3,614 zeros carrying derivation A. These are
the limit-of-quantification suspects — USDA's own docs say "LOQ values are stored as numbers and
component values are stored as 0", and also that "unavailable LOQ values may be reported as
zeros". But the LOQ column **exists only in the live per-food API and is stripped from every bulk
download** (verified: the CSV header is `id, fdc_id, nutrient_id, amount, data_points,
derivation_id, min, max, median, footnote, min_year_acquired` — no `loq`, and no `standard_error`
either). We therefore cannot tell a censored zero from a real one offline, and marking every
analytical zero `below_loq` with a NULL bound would misclassify genuine zeros. `BelowLoq` rows come
from exactly two places: the optional FDC API enrichment pass (§7.4), which returns a real LOQ, and
an OFF `_modifier = '<'`.

### 2.5 Portions

```
grams_per_unit = gram_weight / amount        -- computed once, at ingest
```

`amount` is not always 1 — USDA's own example is "3 tsp" with `amount = 3`. Measured: **3,464 of
14,449 SR Legacy portions have `amount ≠ 1`** (24%); FNDDS has none. Forgetting the division is a
silent 3× mass error that propagates into every nutrient of that entry, so it is done at build time
and the runtime column is a single grams-per-unit scalar.

Label text lives in different columns per dataset — measured:

| Dataset | `portion_description` non-empty | `modifier` non-empty | Rule |
|---|---:|---:|---|
| SR Legacy | **0 / 14,449** | 14,449 | Use `modifier` |
| FNDDS | 22,046 | 22,046 | Use `portion_description` |
| Foundation (469) | 1 / 187 | 94 / 187 | `COALESCE(NULLIF(portion_description,''), NULLIF(modifier,''))`, else `"{gram_weight} g"` |

`measure_unit_id` is `9999 = 'undetermined'` for **100%** of SR Legacy and FNDDS portions. Ignore
the column entirely.

Drop portions with `gram_weight = 0`: that is exactly **1 row** in the whole FNDDS archive. The
belief that this filter removes the 5,326 `"Quantity not specified"` rows is backwards — 5,325 of
those carry a normal non-zero gram weight and are FNDDS's default portion. Keep them.

## 3. The value type

### 3.1 Storage: absence is an absent row

```sql
CREATE TABLE ref_food_nutrients (
  fdc_id      INTEGER NOT NULL,
  nutrient_id INTEGER NOT NULL,
  amount      REAL    NOT NULL CHECK (amount >= 0),   -- ALWAYS the lower bound
  upper_bound REAL,                                   -- NULL  =>  upper == amount
  value_kind  TEXT    NOT NULL CHECK (value_kind IN
                ('measured','calculated','unattributed','assumed_zero',
                 'below_loq','label_zero','trace')),
  source              TEXT    NOT NULL,   -- 'sr_legacy_2018-04' | 'fndds_2024-10-31'
                                          -- | 'foundation_2026-04-30' | 'ars_iodine_r4'
  source_nutrient_id  INTEGER NOT NULL,   -- which chain member won (2047, not 1008)
  derivation_code     TEXT,               -- 'A' | 'Z' | 'NC' | NULL
  data_points         INTEGER,
  low                 REAL,               -- observed min across samples (display only)
  high                REAL,               -- observed max across samples (display only)

  CHECK ((value_kind IN ('below_loq','label_zero','trace')) = (upper_bound IS NOT NULL)),
  CHECK (upper_bound IS NULL OR upper_bound > amount),
  CHECK (value_kind NOT IN ('below_loq','label_zero') OR amount = 0.0),

  PRIMARY KEY (fdc_id, nutrient_id)
) WITHOUT ROWID, STRICT;
```

There is **no NULL amount**, so there is nothing for `COALESCE(amount, 0)` to destroy. "Not
measured" is the absence of the row. All seven invalid states below were confirmed rejected by
SQLite:

| Attempt | Rejected by |
|---|---|
| `upper_bound` on a `measured` value | biconditional CHECK |
| `below_loq` with no `upper_bound` | biconditional CHECK |
| `below_loq` with a non-zero lower | third CHECK |
| `upper_bound <= amount` | second CHECK |
| negative amount | `amount >= 0` |
| unknown `value_kind` string | enum CHECK |
| `NULL` amount | `NOT NULL` |

`(fdc_id, nutrient_id)` is *almost* unique in the source data — the bundled set contains exactly
**one** collision (fdc 2768188 *Alaska Pollock, raw*, nutrient 1106, both rows 2.61). The build
deduplicates deterministically (highest `data_points`, then lowest `food_nutrient.id`) and
**asserts the collision count is ≤ 5**, so a future release that starts colliding fails the build
instead of silently dropping rows.

### 3.2 The type

```rust
// src-tauri/src/nutrition/value.rs
#[derive(Serialize, Deserialize, Clone, Copy, Debug)]
#[serde(tag = "kind", rename_all = "snake_case")]
pub enum NutrientValue {
    /// Lab-analysed. lower == upper == amount.
    Measured     { amount: f64 },
    /// USDA NC/imputed, FNDDS panel, or a recipe roll-up. lower == upper.
    Calculated   { amount: f64 },
    /// A real number with no provenance (SR Legacy blank derivation). lower == upper.
    Unattributed { amount: f64 },
    /// USDA derivation Z: "not naturally occurring / insignificant". 0..0.
    AssumedZero,
    /// Censored below the lab's limit of quantification. 0..upper.
    BelowLoq     { upper: f64 },
    /// A legally-printed 0 under 21 CFR 101.9(c) rounding. 0..upper.
    LabelZero    { upper: f64 },
    /// Reported as "trace". 0..upper.
    Trace        { upper: f64 },
    /// Never stored. Produced only when no row exists. 0..∞.
    Absent,
}

impl NutrientValue {
    pub fn lower(&self) -> f64 { match self {
        Measured{amount} | Calculated{amount} | Unattributed{amount} => *amount,
        AssumedZero | BelowLoq{..} | LabelZero{..} | Trace{..} | Absent => 0.0,
    }}
    /// `None` == unbounded above. There is deliberately no `upper_or_zero()`.
    pub fn upper(&self) -> Option<f64> { match self {
        Measured{amount} | Calculated{amount} | Unattributed{amount} => Some(*amount),
        AssumedZero => Some(0.0),
        BelowLoq{upper} | LabelZero{upper} | Trace{upper} => Some(*upper),
        Absent => None,
    }}
}
```

`#[serde(tag = "kind")]` makes this a TypeScript discriminated union across IPC:

```ts
export type NutrientValue =
  | { kind: 'measured';     amount: number }
  | { kind: 'calculated';   amount: number }
  | { kind: 'unattributed'; amount: number }
  | { kind: 'assumed_zero' }
  | { kind: 'below_loq';    upper: number }
  | { kind: 'label_zero';   upper: number }
  | { kind: 'trace';        upper: number }
  | { kind: 'absent' };
```

A nutrient value **never crosses IPC as a bare `number` or `null`**. That is the entire point:
`Number(null) === 0`, `+null === 0`, `null ?? 0 === 0`, `parseFloat(null) || 0 === 0`, and
`[{se:1},{se:null}].reduce((a,b)=>a+b.se, 0) === 1` — all verified. A discriminated union has no
such coercion; `v.amount` does not type-check on `{kind:'absent'}`.

### 3.3 Aggregation: `[lower, upper]` + coverage

```rust
pub enum Upper { Bounded(f64), AtLeast(f64) }   // AtLeast when some item contributed no row

pub struct DailyNutrient {
    pub nutrient_id: i64,
    pub unit: Unit,
    pub lower: f64,                  // Σ value.lower() × grams/100
    pub upper: Upper,                // Σ value.upper() × grams/100, or AtLeast(that)
    pub items_total: u32,
    pub items_with_data: u32,
    pub items_censored: u32,         // below_loq / label_zero / trace contributors
    pub grams_total: f64,
    pub grams_with_data: f64,
    pub unknown_foods: Vec<String>,  // names, for "3 of 11 foods have no selenium data"
}
impl DailyNutrient {
    /// Mass-weighted, not count-weighted: 200 g of an unmeasured food matters more
    /// than 2 g of one.
    pub fn coverage(&self) -> Option<f64> {
        (self.grams_total > 0.0).then(|| self.grams_with_data / self.grams_total)
    }
}
```

`Upper::AtLeast` is produced whenever `items_with_data < items_total`. An absent value is unbounded
above; pretending otherwise is how a UL check becomes falsely reassuring.

**The asymmetric inference rule.** Unknown values can only *add* to a day's total. Therefore:

| Question | Reads | Rule |
|---|---|---|
| "Am I short?" | `lower` | `lower < RDA` is only *suggestive*; suppress the % entirely when `coverage < 0.5` |
| "Am I over the limit?" | `lower` | **`lower > UL` ⇒ warn with full confidence, regardless of coverage.** Missing data cannot rescue you |
| "Am I safely under the limit?" | `upper` | Only claim this when `upper == Bounded(u)` **and** `u < UL`, i.e. coverage is 1.0. Otherwise say "cannot confirm" |
| "Did I hit my target?" | `lower` and `coverage == 1.0` | A green check requires both |

`coverage < 0.5` (by mass) suppresses the percentage and shows "insufficient data — N of M foods
measured". The threshold is a settings toggle defaulting to 0.5; it is a judgement call, not a
measured constant, and is flagged as such in §8.

**UL warnings fire on a trailing 7-day mean, not a single day.** The UL is defined for routine
daily intake; one serving of liver or four Brazil nuts trips a daily check legitimately and
harmlessly, and users learn to ignore a banner that cries wolf.

**Recipes never launder unknowns.** A recipe's rolled-up value for nutrient *n* is `Absent` unless
**every** ingredient contributed a value for *n*. Eight known ingredients and one unknown produce
`Absent`, not a confident sum. This is the single rule that separates a working micronutrient
screen from a decorative one.

### 3.4 Rendering: three visually distinct things

One formatter module, and an ESLint rule forbidding `.amount` access on a `NutrientValue` anywhere
else.

| Value | Renders | Bar | Chip | Tooltip |
|---|---|---|---|---|
| `Absent` | **`—`** em dash, muted foreground | **no bar track at all** | none | "Not measured for this food" |
| `BelowLoq{0.4}` | **`<0.4 mg`** | hatched segment from 0 to 0.4 | `below detection` | "Measured below the lab's limit of quantification (0.4 mg)" |
| `LabelZero{0.5}` | **`<0.5 g`** | hatched segment | `label rounding` | "The label prints 0; 21 CFR 101.9 permits rounding below 0.5 g" |
| `AssumedZero` | **`0 mg`** | solid bar pinned at 0 | `assumed` | "USDA records this as not naturally occurring in this food" |

## 4. Reference intakes

### 4.1 Sources

| What | Source | Form | Licence |
|---|---|---|---|
| RDA / AI / EAR / UL / AMDR / CDRR | **NASEM DRI Appendix J**, mirrored on NCBI Bookshelf as **NBK545442**, tables `appJ_tab1`–`appJ_tab9` | 9 HTML tables, 2,067 data cells, 1,655 numeric, 347 flagged AI | Values are facts; the layout and footnote prose are copyrighted — we store numbers and write our own captions |
| FDA %DV (28 RDIs + 8 DRVs × 4 population columns) | **eCFR API**, 21 CFR 101.9(c)(8)(iv) and (c)(9) | structured XML, one `curl` | US federal regulation, public domain |
| EER (calorie target) | NASEM 2023 EER equations | transcribed | fact |

Appendix J already folds in the 2011 calcium/vitamin D revision and the 2019 sodium/potassium
revision, and is the current consolidated set as of 2026 (only the EER has been revised since).
There is no authoritative machine-readable DRI dataset; this is the closest thing, and it is a
scrape-and-verify job of one to two days, not weeks.

**Show both numbers.** `%RDA` is primary (it is the product), `%DV` is a smaller secondary line so
the user can reconcile the app with the package in their hand. They diverge by a lot and silently
picking one would systematically mislead: iron DV 18 mg vs adult male RDA 8 mg (225%); phosphorus
1,250 vs 700 (179%); potassium DV 4,700 vs a female AI of 2,600 (181%, because FDA never updated
potassium after the 2019 revision).

### 4.2 Life-stage keying

```sql
CREATE TABLE life_stage_groups (
  id             INTEGER PRIMARY KEY,
  sex            TEXT NOT NULL CHECK (sex IN ('male','female','any')),
  age_min_months INTEGER NOT NULL,
  age_max_months INTEGER,                      -- NULL = open-ended (71+ y)
  condition      TEXT NOT NULL DEFAULT 'none'
                 CHECK (condition IN ('none','pregnancy','lactation')),
  label          TEXT NOT NULL,                -- 'Males 31–50 y'
  UNIQUE (sex, age_min_months, age_max_months, condition)

```

22 rows, including pregnancy and lactation. Transcribe all of them in v1 even though the
pregnancy/lactation UI ships in v1.1 — the data is the same scrape and the verification pass is the
expensive part. Falling a pregnant user back to a non-pregnant row understates folate by 33% and
iron by 33% in the life stage where it matters most.

**Resolve the group from `(birth_date, log_entry.logged_on)`, never from current age.** A user who
crosses 51 has their calcium RDA move 1,000 → 1,200 mg (women) and their chromium AI 25 → 20 µg. If
historical days are scored against today's band, every trend chart develops a discontinuity on the
user's birthday.

### 4.3 Targets and limits

```sql
CREATE TABLE reference_intakes (
  life_stage_id INTEGER NOT NULL REFERENCES life_stage_groups(id),
  nutrient_id   INTEGER NOT NULL REFERENCES nutrients(nutrient_id),
  kind          TEXT NOT NULL CHECK (kind IN ('rda','ai','ear','amdr_min','amdr_max','cdrr')),
  amount        REAL NOT NULL,
  unit          TEXT NOT NULL,
  dataset       TEXT NOT NULL,                 -- 'nasem-dri-appJ-2019'
  PRIMARY KEY (life_stage_id, nutrient_id, kind)
) WITHOUT ROWID, STRICT;

CREATE TABLE upper_limits (
  life_stage_id     INTEGER NOT NULL REFERENCES life_stage_groups(id),
  nutrient_id       INTEGER NOT NULL REFERENCES nutrients(nutrient_id),
  status            TEXT NOT NULL CHECK (status IN ('ul','cdrr','none_established')),
  amount            REAL,
  unit              TEXT,
  applies_to        TEXT NOT NULL CHECK (applies_to IN
                      ('total_intake','preformed_only','synthetic_or_fortified',
                       'supplemental_only','not_applicable')),
  -- the nutrient the evaluator ACTUALLY sums. Not necessarily nutrient_id.
  source_nutrient_id INTEGER REFERENCES nutrients(nutrient_id),
  note_key          TEXT,                      -- key into our own caption strings
  dataset           TEXT NOT NULL,

  CHECK ((amount IS NULL) = (status = 'none_established')),
  CHECK ((applies_to = 'supplemental_only') = (source_nutrient_id IS NULL)),
  CHECK (status <> 'none_established' OR applies_to = 'not_applicable'),
  PRIMARY KEY (life_stage_id, nutrient_id)
) WITHOUT ROWID, STRICT;
```

**`status = 'none_established'` forces `amount = NULL`, and a NULL amount is impossible to render
as "unlimited"** — the formatter has no numeric branch to take, so it emits "No upper limit
established" with the sub-caption "in the absence of a UL, caution is warranted above recommended
intakes". `status = 'cdrr'` renders as a ceiling to reduce toward, not a target to fill.

**How a UL warning is made structurally unable to fire on food-source vitamin A or food folate.**
The evaluator does not read the target's nutrient. It reads `upper_limits.source_nutrient_id` and
looks up *that* row of the daily rollup. Since the rollup is keyed by `nutrient_id`, the vitamin A
UL literally cannot see 1106.

| Nutrient (target) | `applies_to` | UL evaluator sums | Consequence |
|---|---|---|---|
| Vitamin A, RAE (1106) | `preformed_only` | **1105 Retinol** | A carrot-and-sweet-potato day cannot trip hypervitaminosis A. The UL is 3,000 µg/day of *preformed* vitamin A — retinol and retinyl esters — not total RAE |
| Folate (1190 / 1177) | `synthetic_or_fortified` | **1186 Folic acid** | Food folate cannot trip the 1,000 µg limit |
| Niacin (1167) | `synthetic_or_fortified` | **1245 Niacin, added** | The NASEM footnote covers supplements *and fortified foods*, so fortified-cereal niacin does count — restricting to user-entered supplements would under-warn |
| Vitamin E (1109) | `synthetic_or_fortified` | **1242 Vitamin E, added** | Same reasoning |
| Magnesium (1090) | `supplemental_only` | *(nothing — `source_nutrient_id` is NULL)* | The 350 mg UL is supplemental-only. A normal diet exceeds it routinely; comparing food magnesium against it would warn most users most days and destroy trust in every other warning. In v1 (no supplement log) this renders "not evaluated from food intake" |
| Everything else | `total_intake` | itself | |

Four golden assertions in the build, so a re-scrape cannot regress this:
`(1106 → 1105)`, `(1190 → 1186)`, `(1167 → 1245)`, `(1109 → 1242)`.

**Nutrients with no UL at all.** In the tracked set: **vitamin K, thiamin, riboflavin, pantothenic
acid, biotin, vitamin B12, chromium, potassium**, plus the carotenoids and water. **Sodium has no
UL either** — the 2019 revision withdrew it and replaced it with a **CDRR of 2,300 mg/day**, which
is a reduce-toward ceiling, not a limit. For all of these the UI says "no upper limit established",
never "safe" and never a bar at 0%.

**AI vs RDA is a first-class column, not a tooltip.** `kind = 'ai'` changes the copy, because an AI
means the evidence was insufficient to set an RDA:

- RDA: `Target 90 mg (RDA)`, and falling short may be called a shortfall.
- AI: `Adequate Intake 120 µg`, sub-copy `Below the AI, adequacy cannot be determined` — and the
  bar is drawn in a distinct, non-alarming treatment.

**Chromium and biotin have AIs, not RDAs** (chromium 35 µg men / 25 µg women; biotin 30 µg
adults), and neither has a UL. Labelling either as an RDA, or drawing a red "0 / 35 µg — 0%" bar
for chromium (which has zero rows in every bundleable dataset), is wrong twice over.

**`is_limit` nutrients** — sodium, saturated fat, trans fat, added sugars, cholesterol — render as
ceilings, not targets: the bar fills toward a limit and turns amber past it, and there is no
"you're short" state.

## 5. The SQLite schema

### 5.1 Two files, not one — resolving the disagreement

The two research tracks disagreed. The one-file argument was: FKs cannot cross an `ATTACH`
boundary; `ATTACH` is per-connection state on a 10-connection pool the app cannot configure; and
`journal_mode` is never set, so you silently get DELETE instead of WAL.

**Every one of those three is a property of `tauri-plugin-sql`/sqlx, and we are not using it.** The
plugin hardcodes `Pool::connect()` with sqlx's default `max_connections: 10` and exposes no
`after_connect` hook, so per-connection `ATTACH` and PRAGMAs land on one arbitrary pooled
connection and expire with it. With `rusqlite` we own every `Connection` and set its PRAGMAs at
open. The objection evaporates.

Two additional facts make the plugin a non-starter independently of file count: Cargo forbids two
crates declaring `links = "sqlite3"`, and `tauri-plugin-sql` → `sqlx 0.8` → `libsqlite3-sys 0.30.1`
(SQLite **3.45.3**) collides with `rusqlite 0.40` → `libsqlite3-sys 0.38.x` (SQLite **3.51.3**) — so
it is one or the other, decided up front. And the plugin's `select` returns untyped
`IndexMap<String, JsonValue>` with decode failures mapped to `JsonValue::Null`, which puts a bare
`null` on the IPC wire for a nutrient value. That is §3.2's failure mode, promoted to a library
guarantee.

**So: two files.**

| File | Path | Mode | Contents |
|---|---|---|---|
| `usda_core.db` | macOS `app_data_dir()/reference/`, Android `app_data_dir()/no_backup/reference/` | read-only, `SQLITE_OPEN_READ_ONLY \| SQLITE_OPEN_NO_MUTEX` | `nutrients`, `ref_foods`, `ref_food_nutrients`, `ref_food_portions`, `ref_foods_fts`, `life_stage_groups`, `reference_intakes`, `upper_limits`, `daily_values`, `meta` |
| `user.db` | `app_data_dir()/` | WAL, `foreign_keys=ON`, `busy_timeout=5000` | everything the user authored, plus snapshots and the online cache |

What this buys, in order of importance:

1. **"Ship a newer USDA release without clobbering user data" becomes structurally impossible to
   get wrong.** The reference DB is replaced by file rename; user data is in a different file and
   is never touched by a data refresh. In a one-file design, the biannual USDA refresh becomes a
   schema migration over the user's live database.
2. Omitting the `CREATE` flag on the read-only open turns a failed asset extraction into a loud
   error instead of a mysteriously empty app.
3. The shipped file contains only CC0 USDA + public-domain DRI values. ODbL-licensed OFF rows live
   in `user.db` and cannot leak into anything distributable.
4. Android Auto Backup has a 25 MB quota. An 18 MiB reference DB inside backed-up app data would
   silently kill backup of the user's actual food log. Hence `no_backup/` on Android.

The cost — no FK from `log_entries` to `ref_foods` — is a cost we would pay anyway, because a
future USDA release can *remove* an `fdc_id`. §5.3 handles it properly with snapshots.

**Android extraction, once, in `setup()`:** resolve `resources/usda_core.db` with
`BaseDirectory::Resource`; open it with `app.fs().open(src, OpenOptions::new().read(true))` — which
falls through to `std::fs` on desktop and detects the `asset://localhost/` prefix on Android; stream
`std::io::copy` into `usda_core.db.partial` while feeding a SHA-256; compare against the constant
`build.rs` computed from the packaged file; `rename()`; write the hash to `usda_core.stamp`; delete
Android's `cacheDir/_assets/` copy. Do **not** use `app.fs().read()` (whole file into a `Vec<u8>`)
and do **not** use `std::fs::File::open` (returns `ENOENT` on Android, because
`PathPlugin.getResourcesDir` returns the literal string `"asset://localhost/"`, which is not a
filesystem path). Keep the `.db` extension and do **not** add `noCompress += "db"` to the Gradle
config: `.db` being compressed is what routes tauri-plugin-fs onto its correct decompress-to-cache
path, and its `openFd` path discards `AssetFileDescriptor.getStartOffset()`.

### 5.2 LONG, not WIDE

Four reasons, in decreasing order of force:

1. **Provenance is per-value.** Every value carries `value_kind`, `upper_bound`, `source`,
   `source_nutrient_id`, `derivation_code`, `data_points`. Wide would need six columns per nutrient
   — 74 × 6 = 444 columns — which is unmaintainable and near SQLite's practical limits.
2. **Absence must be representable as an absent row.** Wide forces `NULL` in every unmeasured cell,
   and `NULL` is one `COALESCE` from `0`. Long removes the NULL entirely (§3.1).
3. **Adding a nutrient is an INSERT, not an `ALTER TABLE`** on an 18 MiB shipped file.
4. **Performance does not decide it.** The measured daily rollup is **0.145 ms** over a
   2,193-entry year (§6). Both layouts are far inside budget, so the design budget goes to
   correctness.

```sql
  food_id TEXT NOT NULL REFERENCES cached_foods(id) ON DELETE CASCADE,
  nutrient_id INTEGER NOT NULL,
  amount REAL NOT NULL CHECK (amount >= 0), upper_bound REAL,
  value_kind TEXT NOT NULL CHECK (value_kind IN
    ('measured','calculated','unattributed','assumed_zero','below_loq','label_zero','trace')),
  CHECK ((value_kind IN ('below_loq','label_zero','trace')) = (upper_bound IS NOT NULL)),
  CHECK (upper_bound IS NULL OR upper_bound > amount),
  CHECK (value_kind NOT IN ('below_loq','label_zero') OR amount = 0.0),
  PRIMARY KEY (food_id, nutrient_id)
) WITHOUT ROWID, STRICT;

-- ---------- recipes ----------
CREATE TABLE recipes (
  id            TEXT PRIMARY KEY,
  profile_id    TEXT NOT NULL REFERENCES profiles(id),
  name          TEXT NOT NULL,
  yield_grams   REAL CHECK (yield_grams > 0),   -- MEASURED cooked weight; NULL = sum of inputs
  yield_servings REAL CHECK (yield_servings > 0),
  cook_method   TEXT CHECK (cook_method IN ('raw','boiled','steamed','roasted','fried','baked','other')),
  notes         TEXT,
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL, deleted_at TEXT
) STRICT;

CREATE TABLE recipe_items (
  id             TEXT PRIMARY KEY,
  recipe_id      TEXT NOT NULL REFERENCES recipes(id) ON DELETE CASCADE,
  position       INTEGER NOT NULL,
  component_kind TEXT NOT NULL CHECK (component_kind IN ('usda','cached','custom','recipe')),
  component_ref  TEXT NOT NULL,
  grams          REAL NOT NULL CHECK (grams > 0),
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL, deleted_at TEXT,
  CHECK (component_ref <> recipe_id)            -- cheap self-reference guard
) STRICT;

-- ---------- the log ----------
CREATE TABLE nutrient_snapshots (
  id              TEXT PRIMARY KEY,    -- sha256(source_kind, source_ref, dataset_version,
                                       --        sorted (nutrient_id, amount, upper_bound, value_kind))
  source_kind     TEXT NOT NULL CHECK (source_kind IN ('usda','cached','custom','recipe')),
  source_ref      TEXT NOT NULL,
  dataset_version TEXT NOT NULL,       -- 'sr_legacy_2018-04' | 'off@2026-09-03' | 'custom@<updated_at>'
  basis_grams     REAL NOT NULL DEFAULT 100 CHECK (basis_grams > 0),
  created_at      TEXT NOT NULL
) STRICT;

CREATE TABLE snapshot_nutrients (
  snapshot_id TEXT NOT NULL REFERENCES nutrient_snapshots(id) ON DELETE CASCADE,
  nutrient_id INTEGER NOT NULL,        -- no FK: `nutrients` lives in the other file
  amount REAL NOT NULL CHECK (amount >= 0), upper_bound REAL,
  value_kind TEXT NOT NULL CHECK (value_kind IN
    ('measured','calculated','unattributed','assumed_zero','below_loq','label_zero','trace')),
  CHECK ((value_kind IN ('below_loq','label_zero','trace')) = (upper_bound IS NOT NULL)),
  CHECK (upper_bound IS NULL OR upper_bound > amount),
  CHECK (value_kind NOT IN ('below_loq','label_zero') OR amount = 0.0),
  PRIMARY KEY (snapshot_id, nutrient_id)
) WITHOUT ROWID, STRICT;

CREATE TABLE log_entries (
  id                TEXT PRIMARY KEY,
  profile_id        TEXT NOT NULL REFERENCES profiles(id),
  logged_on         TEXT NOT NULL,      -- 'YYYY-MM-DD', LOCAL calendar date
  logged_at         TEXT NOT NULL,      -- UTC instant
  tz_offset_minutes INTEGER NOT NULL,   -- offset in force when logged
  meal              TEXT NOT NULL CHECK (meal IN ('breakfast','lunch','dinner','snack')),
  sort_order        INTEGER NOT NULL DEFAULT 0,

  -- POLYMORPHIC BREADCRUMB, not an integrity constraint:
  food_kind    TEXT NOT NULL CHECK (food_kind IN ('usda','cached','custom','recipe')),
  food_ref     TEXT NOT NULL,           -- fdc_id | cached_foods.id | custom_foods.id | recipes.id
  food_label   TEXT NOT NULL,           -- denormalised name AT LOG TIME

  quantity      REAL NOT NULL CHECK (quantity > 0),
  portion_label TEXT,                   -- NULL = the user typed grams
  grams         REAL NOT NULL CHECK (grams > 0),

  -- THE integrity-bearing reference:
  snapshot_id TEXT NOT NULL REFERENCES nutrient_snapshots(id),

  created_at TEXT NOT NULL, updated_at TEXT NOT NULL, deleted_at TEXT
) STRICT;
```

**On polymorphism.** `(food_kind, food_ref)` cannot be a foreign key: two of its four targets live
in another database file, and USDA can delete an `fdc_id` between releases. So it is demoted to
what it actually is — a breadcrumb powering "log this again" and "open food details", allowed to
dangle. The reference that *must not* dangle is `snapshot_id`, and it is a real FK inside
`user.db`. This is why a USDA release update, a cache eviction, and a deleted custom food are all
non-events for historical totals: **the numbers were copied into the log at write time.**

The two breadcrumb targets that *do* live in `user.db` are still validated, by trigger:

```sql
CREATE TRIGGER trg_log_entries_ref_ai AFTER INSERT ON log_entries
WHEN NEW.food_kind IN ('custom','recipe') BEGIN
  SELECT CASE WHEN NOT EXISTS (
      SELECT 1 FROM custom_foods WHERE NEW.food_kind='custom' AND id = NEW.food_ref
      UNION ALL
      SELECT 1 FROM recipes      WHERE NEW.food_kind='recipe' AND id = NEW.food_ref)
    THEN RAISE(ABORT, 'log_entries.food_ref does not resolve') END;
END;
-- plus the matching AFTER UPDATE OF food_kind, food_ref trigger.
```

Deleting a custom food or recipe is **soft only**, and the UI blocks it behind "used in N log
entries — hide it instead?". A hard `DELETE` with `foreign_keys=ON` would either fail or, worse,
cascade.

**Timezone.** A food-log day is a local-calendar concept, not an instant. Storing only
`logged_at` and deriving the day at query time means a flight across a date line silently moves
yesterday's dinner. `logged_on` is authoritative for the dashboard; `logged_at` and
`tz_offset_minutes` exist for audit and for sync ordering.

**Recipes.** Nesting via `component_kind = 'recipe'`, depth capped at 5, resolved at read time —
never materialised, so editing an ingredient fixes every recipe that uses it. Cycles are caught by
a recursive CTE before any write:

```sql
WITH RECURSIVE expand(root, node, depth) AS (
  SELECT :recipe_id, :recipe_id, 0
  UNION ALL
  SELECT e.root, ri.component_ref, e.depth + 1
    FROM expand e
    JOIN recipe_items ri ON ri.recipe_id = e.node
                        AND ri.component_kind = 'recipe'
                        AND ri.deleted_at IS NULL
   WHERE e.depth < 6
)
SELECT max(depth) AS depth, sum(node = :recipe_id AND depth > 0) AS cycles FROM expand;
-- reject if cycles > 0 OR depth > 5
```

**Yield and cooking loss.** `yield_grams` is the *measured cooked weight*. Nutrients concentrate or
dilute by mass: `per_100g_cooked = Σ(ingredient_amount × grams/100) / yield_grams × 100`. We
deliberately do **not** model heat-labile losses. SR Legacy ships `retention_factor.csv`, but it is
**270 rows of `(id, code, food_group_id, description)` — code descriptions only, with no retention
percentages per nutrient**, so the bundle contains nothing usable. Modelling cooking loss as mass
change alone systematically overstates vitamin C, folate, thiamin and B6 for anything boiled;
recipes with `cook_method <> 'raw'` therefore carry a visible "raw-basis; heat-sensitive vitamins
may be overstated" caption rather than a silent wrong number.

**Targets.**

```sql
CREATE TABLE nutrient_targets (
  id             TEXT PRIMARY KEY,
  profile_id     TEXT NOT NULL REFERENCES profiles(id),
  nutrient_id    INTEGER NOT NULL,
  effective_from TEXT NOT NULL,          -- local date; targets are time-sliced, not overwritten
  effective_to   TEXT,
  target_kind    TEXT NOT NULL CHECK (target_kind IN ('rda','ai','ear','amdr','cdrr','custom')),
  min_amount     REAL,
  max_amount     REAL,
  max_status     TEXT NOT NULL CHECK (max_status IN ('ul','cdrr','none_established','not_applicable')),
  max_applies_to TEXT,
  max_source_nutrient_id INTEGER,
  source         TEXT NOT NULL,          -- 'nasem-dri-appJ-2019' | 'user'
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL, deleted_at TEXT,
  CHECK ((max_amount IS NULL) = (max_status IN ('none_established','not_applicable')))
) STRICT;
```

Targets are **derived** from `profiles` + `reference_intakes` at profile-change time and written
here as a time-sliced row, so a historical day is always scored against the target that was in
force. A user override is the same table with `source = 'user'`.

**Indexes — these and no more for v1.**

```sql

CREATE INDEX ix_log_snapshot  ON log_entries(snapshot_id)                              WHERE deleted_at IS NULL;

CREATE VIRTUAL TABLE user_foods_fts USING fts5(
  name, brand, kind UNINDEXED, ref_id UNINDEXED,
  prefix='2 3', tokenize="unicode61 remove_diacritics 2");

-- maintained by INSERT/UPDATE/DELETE triggers on each. Searched alongside

```

**Migrations.** `rusqlite_migration` driving `PRAGMA user_version`, on `user.db` only. The
reference DB is versioned by *replacement*, never migration. Two hard rules: never edit a shipped
migration, and store a checksum of each applied migration (`rusqlite_migration`, unlike sqlx's
`Migrator`, will not catch an edited already-applied migration on its own).

## 6. The daily rollup query

### 6.1 The bug to avoid

A proposed rollup read `FROM nutrients n CROSS JOIN day d LEFT JOIN …`, where `day` is a CTE of the
day's log entries. Its stated rationale — "join outward from the nutrients dimension so every
tracked nutrient produces a row" — is right; the SQL does the opposite. **A `CROSS JOIN` against an
empty CTE yields zero rows**, so on a day with nothing logged every tracked nutrient disappears and
the dashboard renders blank instead of showing all 74 nutrients as unmet. Reproduced verbatim:

```
BROKEN query, empty day -> 0 rows          # should be 74
BROKEN query, full  day -> 74 rows         # looks fine in dev, which is why it ships
```

The fix is not to remove the cross join — it is to cross-join against something that is
**guaranteed to return exactly one row**. A bare aggregate with no `GROUP BY` does that: `SELECT
COUNT(*), COALESCE(SUM(grams), 0.0) FROM day_items` returns one row of `(0, 0.0)` over an empty
input.

### 6.2 The query

```sql
-- src-tauri/src/sql/daily_rollup.sql
-- Params: :profile, :day ('YYYY-MM-DD' local).
-- Runs on user.db with usda_core.db ATTACHed as `ref`.
WITH day_items AS (
    SELECT le.id AS entry_id, le.snapshot_id, le.grams, le.food_label,
           le.grams / s.basis_grams AS factor
      FROM log_entries le
      JOIN nutrient_snapshots s ON s.id = le.snapshot_id
     WHERE le.profile_id = :profile
       AND le.logged_on  = :day
       AND le.deleted_at IS NULL
),
day_totals AS (                       -- bare aggregate: ALWAYS exactly one row
    SELECT COUNT(*) AS items_total, COALESCE(SUM(grams), 0.0) AS grams_total
      FROM day_items
),
contrib AS (
    SELECT sn.nutrient_id,
           SUM(sn.amount * di.factor)                           AS lower_sum,
           SUM(COALESCE(sn.upper_bound, sn.amount) * di.factor) AS upper_sum,
           COUNT(*)                                             AS items_with_data,
           SUM(di.grams)                                        AS grams_with_data,
           SUM(sn.value_kind IN ('below_loq','label_zero','trace')) AS items_censored
      FROM day_items di
      JOIN snapshot_nutrients sn ON sn.snapshot_id = di.snapshot_id
     GROUP BY sn.nutrient_id
)
SELECT n.nutrient_id,
       n.name,
       n.unit,
       c.lower_sum                      AS lower,          -- NULL <=> nothing contributed
       c.upper_sum                      AS upper_known,    -- NULL <=> nothing contributed
       COALESCE(c.items_with_data, 0)   AS items_with_data,
       t.items_total,
       COALESCE(c.grams_with_data, 0.0) AS grams_with_data,
       t.grams_total,
       CASE WHEN COALESCE(c.items_with_data,0) = t.items_total AND t.items_total > 0
            THEN 1 ELSE 0 END           AS upper_is_bounded,
       COALESCE(c.items_censored, 0)    AS items_censored
  FROM ref.nutrients n
  JOIN day_totals   t                                       -- 1 row, unconditionally
  LEFT JOIN contrib c ON c.nutrient_id = n.nutrient_id
 WHERE n.is_tracked = 1
 ORDER BY n.display_order, n.nutrient_id;
```

Four things to notice:

1. `lower` and `upper_known` are **left NULL** when nothing contributed. Rust maps NULL to
   `DailyNutrient { upper: AtLeast(0.0), items_with_data: 0, .. }`, which the formatter renders as
   `—`. The counts and masses *are* `COALESCE`d, because "zero foods, zero grams" is genuinely
   known — that is the distinction between a legitimate `COALESCE` and the banned one.
2. `COALESCE(sn.upper_bound, sn.amount)` is legal for the same reason: both operands are known
   numbers from the same row, chosen by a CHECK-enforced biconditional. It is not standing in for
   missing data.
3. `upper_is_bounded` is the flag that stops a UL check from ever saying "you're fine" on partial
   data.
4. `grams_with_data / grams_total` is **mass**-weighted coverage. 200 g of an unmeasured food
   should count for more than 2 g of one.

### 6.3 Verified

Fixture: 91 g broccoli (Se measured 2.5 µg/100 g, Fe `below_loq` upper 0.4), 113 g ground beef
(Se 24.0, Fe 2.6 measured), 28 g potato chips (Fe `label_zero` upper 0.36, **no selenium row at
all**).

```
=== 2026-09-03 (3 entries) ===  74 rows
Selenium  lower=29.395  upper_known=29.395  items 2/3  grams 204/232  bounded=0  censored=0
Iron      lower=2.938   upper_known=3.4028  items 3/3  grams 232/232  bounded=1  censored=2

=== 2026-09-04 (empty day) ===  74 rows
every row: lower=NULL upper=NULL items 0/0 grams 0/0 bounded=0

OK: both days return exactly 74 tracked-nutrient rows.
OK: interval arithmetic and coverage are correct.

one-day rollup over a 2,193-entry year: 0.145 ms/query
```

Selenium is `29.4 µg`, `upper_is_bounded = 0`, coverage `204/232 = 88%` — the chips contributed
mass but no selenium row, so the true upper bound is unbounded and the UI must say so. Iron is
`2.94–3.40 mg` with full coverage and two censored contributors — a genuine interval, rendered as a
range with a hatched bar segment. Neither is a scalar, and that is the whole design.

Trend queries are the same CTEs with `logged_on BETWEEN :from AND :to` and `GROUP BY logged_on,
nutrient_id`. **No `daily_summary` materialisation in v1** — at 0.145 ms there is no case for a
cache that can go stale.

## 7. Ingest pipeline

Everything is a checked-in script. Nothing is done by hand.

```
scripts/
  fetch-sources.sh          # download + sha256-verify + extract into data/raw/
  sources.sha256            # COMMITTED manifest of the four archives
  build-reference-db/       # standalone Rust crate; pins the SAME rusqlite as the app
    Cargo.toml
    src/main.rs
  scrape-dri.py             # NASEM appJ + eCFR  ->  data/reference/dri.json
  assertions.toml           # COMMITTED golden row counts and invariants
data/
  raw/                      # gitignored (already)
  reference/dri.json        # COMMITTED, hand-verified
src-tauri/
  resources/usda_core.db    # GENERATED, gitignored
  build.rs                  # hashes resources/usda_core.db -> USDA_CORE_SHA256 const
```

### 7.1 `fetch-sources.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail
RAW="$(cd "$(dirname "$0")/.." && pwd)/data/raw"
mkdir -p "$RAW/extracted"
base=https://fdc.nal.usda.gov/fdc-datasets
files=(
  "$base/FoodData_Central_foundation_food_csv_2026-04-30.zip"   # 3,825,741 bytes
  "$base/FoodData_Central_sr_legacy_food_csv_2018-04.zip"       # 6,074,592 bytes
  "$base/FoodData_Central_survey_food_csv_2024-10-31.zip"       # 3,325,692 bytes
  "https://www.ars.usda.gov/ARSUserFiles/80400535/Data/Iodine/IODINE_RELEASE_4.zip"
)
for u in "${files[@]}"; do
  [[ -f "$RAW/$(basename "$u")" ]] || curl -fL --retry 3 -o "$RAW/$(basename "$u")" "$u"
done
( cd "$RAW" && shasum -a 256 -c ../../scripts/sources.sha256 )   # fail loudly on drift
for z in "$RAW"/*.zip; do unzip -qo "$z" -d "$RAW/extracted/$(basename "$z" .zip)"; done
mv -f "$RAW/extracted/IODINE_RELEASE_4" "$RAW/extracted/iodine" 2>/dev/null || true
```

Note the filename: **`..._foundation_food_csv_2026-04-30.zip`**. The plausible-looking
`2026-04-24` returns HTTP 404 — that suffix belongs to the 2025 release. Foundation refreshes twice
a year, but the second release has landed in October *and* in December (2024-10-31, 2025-12-18), so
do not schedule around a date.

### 7.2 `build-reference-db` — why Rust, not TypeScript

The builder pins **the same `rusqlite = { version = "0.40", features = ["bundled"] }`** the app
ships, so the writer and the reader are byte-identical SQLite 3.51.3. That matters concretely: FTS5
tokenizer options and `STRICT`/`WITHOUT ROWID` handling must match between the tool that writes the
index and the library that reads it, and the system `sqlite3` on this machine is **3.40.1** — old
enough to be a different FTS5 build. A TypeScript builder would need `better-sqlite3`, i.e. a third
SQLite version in the mix. `cargo run --release -p build-reference-db` removes the whole class.

Pipeline, in order:

1. **Load `nutrient.csv`** (477 rows). Build both `id → row` and `nutrient_nbr → id`. `rank` is a
   float-formatted string (`'5400.0'`) — cast, do not parse as int.
2. **Select foods.** Foundation: `food.csv WHERE data_type='foundation_food'` → 469. SR Legacy:
   all 7,793. FNDDS: all 5,432. Load `foundation_food.csv` and `sr_legacy_food.csv` for
   `NDB_number` only.
3. **Load nutrient values.** Foundation and SR join on `nutrient.id`; **FNDDS joins on
   `nutrient.nutrient_nbr`** (§2.3). Map derivation → `value_kind` per §2.4. Apply the §2.2
   resolution chains, recording `source_nutrient_id`. Deduplicate `(fdc_id, nutrient_id)`; assert
   collisions ≤ 5. Discard untracked nutrient ids (369,486 rows).
4. **Overlay iodine** (§1.3): parse column B with the five-form matcher, resolve to `fdc_id`, write
   `nutrient_id = 1100` rows with `source='ars_iodine_r4'`. Report unresolved codes.
5. **Load portions**, computing `grams_per_unit = gram_weight / amount`; label per §2.5; drop
   `gram_weight = 0`.
6. **Load `data/reference/dri.json`** into `life_stage_groups` / `reference_intakes` /
   `upper_limits` / `daily_values`.
7. **Build FTS5**, then `INSERT INTO ref_foods_fts(ref_foods_fts) VALUES('optimize')`.
8. **Assert, then `VACUUM; ANALYZE; PRAGMA integrity_check;`**, write `meta`, and print the file
   size.

### 7.4 Optional LOQ enrichment (post-v1)

The limit of quantification exists **only in the live per-food FDC API**, never in a bulk download.
A one-off pass over the ~4,100 Foundation zeros, at 1,000 requests/hour with a personal key, takes
about five hours and converts a real fraction of them from `Measured{0.0}` into
`BelowLoq{upper: loq}` — which is *more* information, not less. It writes a checked-in
`data/reference/loq-overlay.json` so the enrichment is done once and replayed by every build. Not
in v1; the design already handles the values, so this is data, not schema.

### 7.5 Committed or generated?

**Generated.** `src-tauri/resources/*.db` is gitignored.

- 17.88 MiB of binary that changes *wholesale* twice a year. Git cannot delta a SQLite file
  usefully; five releases is ~90 MiB of history for data that is freely re-derivable.
- The build is reproducible from committed inputs: `sources.sha256` pins the archives byte-for-byte
  and `assertions.toml` pins the output. Reproducibility is asserted on **row counts and a content
  digest over sorted rows** (`meta.row_digest`), not on file bytes — SQLite's page layout is not
  bit-reproducible in general.
- `build.rs` computes the SHA-256 of the packaged `usda_core.db` at compile time and emits it as a
  const, which the first-launch extraction (§5.1) compares against. Nobody types a hash by hand.

What *is* committed: `scripts/**`, `sources.sha256`, `assertions.toml`, and
**`data/reference/dri.json`** — small, hand-verified, and expensive enough to re-derive that it
should never be regenerated silently. `dri.json` is compared against a golden copy in CI so a
re-scrape that shifts a value fails review rather than shipping.

## 8. Open questions

| # | Question | Safe default shipped in v1 |
|---|---|---|
| 1 | Coverage threshold below which %RDA is suppressed | **0.5 by mass**, exposed as a settings toggle. This is a judgement call, not a measured constant |
| 2 | Does the FDC API support exact GTIN lookup (`gtinUpc:<code>`), or only fuzzy text search? | Unverified. Resolution order tries FDC first and falls through to OFF on a non-exact match; if FDC exact lookup proves unsupported, swap the order — one config constant |

| 4 | Should EAR (not 100% RDA) be the "likely inadequate" threshold? | Ship RDA/AI as the headline. EAR is transcribed and stored, so switching later is a UI change |
| 5 | Non-binary users and users who decline to state sex | `sex_at_birth = 'unspecified'` plus an explicit `life_stage_override`. Averaging the male and female DRI rows produces a number that describes nobody; ask instead |
| 6 | Children's profiles in v1? | No. Transcribe the rows, ship adults only. Infant nutrition is entirely AI-based and a food log is the wrong tool |
| 7 | Snapshot the day's targets, or recompute from profile + dataset version? | **Recompute** — `nutrient_targets` is time-sliced by `effective_from`, so a transcription fix propagates to history, which is what you want for a bug and not for a genuine life-stage change |
| 8 | What happens to historical logs when USDA revises a value? | Nothing — snapshots are immutable. Surface the discrepancy in food details ("this food's iron changed from 2.6 to 2.9 mg in the 2026-12 release"); never rewrite the log |
| 9 | An opt-in "estimate unknowns from category medians" mode? | Not in v1. If ever built, it must never be the default and must never feed the UL check |
